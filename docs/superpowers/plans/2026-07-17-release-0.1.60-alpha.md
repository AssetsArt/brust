## Goal

Publish the reviewed imported-static-const native-inline fix as `brustjs` `0.1.60-alpha`, including all six native platform packages and `create-brustjs`.

## Non-goals

- No additional compiler or runtime behavior changes.
- No manual version edits, feature-branch tags, CI bypasses, or partial package publish.
- No modification of the external `ket-doc` consumer.

## Decisions

1. Increment the alpha line from `0.1.59-alpha` to `0.1.60-alpha`.
2. Follow the repository release skill exactly: PR, green CI, merge, main-only version bump, main-only tag, release watch.
3. Use the existing merge-commit convention so the reviewed commits remain traceable.
4. Treat any red or pending GitHub check as a hard stop before merge or tag.

## Implementation Boundary

- The feature PR contains the reviewed compiler change, its canonical plans, and no version bump.
- The post-merge release bump may edit only the root, `create-brustjs`, and six `npm/*/package.json` version files named in the execution header.
- GitHub state changes are limited to the release PR, its merge, the `main` push, and tag `v0.1.60-alpha` explicitly authorized by the human.

## Ordered edits

1. Dabin runs the exact pre-flight matrix and opens the PR without changing source behavior.
2. Aoki waits for green GitHub CI and merges the PR.
3. Aoki runs `bun scripts/release-bump.ts 0.1.60-alpha`, verifies 15/15 refs, and commits on `main`.
4. Aoki creates and pushes annotated tag `v0.1.60-alpha`, then watches `release.yml`.

## Verification

- Run every local command listed in the execution-header gates in the skill-defined order.
- Require all PR checks green before merge.
- Require `release.yml` success after the tag push.
- Verify npm versions and `alpha`/`latest` dist-tags for `brustjs` and `create-brustjs`.

## Risks

- `release.yml` publishes even when `ci.yml` is red; Aoki is the explicit gate.
- A partial version bump breaks immutable npm package coordination; only `release-bump.ts` is allowed.
- Tagging before merge or from a feature branch would publish the wrong commit; tag ancestry is verified against `main` before push.

## Rejected alternatives

- Directly pushing the feature commits to `main`: rejected because the release skill requires a reviewed PR and green GitHub CI.
- Bumping versions in the feature PR: rejected because the bump must happen on merged `main`.
- Using `workflow_dispatch` as publish: rejected because it validates builds but does not publish.

## Authority and roles

- Aoki owns the release, integration, version bump, main tag, and final outcome.
- Dabin owns the exact pre-flight gate run and opening the PR from `feat/imported-static-const-native-inline-release` to `main`.
- Armin reviews the PR diff and release readiness if CI or scope evidence conflicts.
- Authority is in-loop. The human explicitly authorized publishing this release.

## Mandatory order

1. Run every pre-flight command from `.claude/skills/release/SKILL.md` on the feature branch.
2. Push `feat/imported-static-const-native-inline-release` and open a PR to `main`.
3. Wait for every required GitHub check to pass. Do not tag while the PR is open or red.
4. Merge using the repository's merge-commit convention and update local `main` with `--ff-only`.
5. On `main`, run `bun scripts/release-bump.ts 0.1.60-alpha`, verify all 15 refs, and commit `chore(release): 0.1.60-alpha`.
6. Create annotated tag `v0.1.60-alpha` on that main release commit. Push `main`, then push the tag.
7. Watch `release.yml` to success and verify the npm versions/dist-tags.

## Constraints

- Never tag the feature branch.
- Never bypass or race a red/pending `ci.yml` check.
- Use `scripts/release-bump.ts`; do not hand-edit version references.
- Do not amend or rewrite the reviewed implementation commits.
- If GitHub reports a failing check, record the exact run/log evidence before proposing any fix.

## Escalation

Aoki owns all release rulings with authority in-loop. Dabin files pre-flight or PR conflicts as task challenges. Armin files review findings as task challenges. Publishing `v0.1.60-alpha` is explicitly authorized; any different version or broader publish target is a scope change and must return to the human.

## Done When

- The main-bound PR is merged with green CI.
- `v0.1.60-alpha` points to the version-bump commit on `main`.
- `release.yml` succeeds for all platform builds and publish.
- npm exposes `brustjs@0.1.60-alpha` and `create-brustjs@0.1.60-alpha` under the expected alpha/latest tags.
