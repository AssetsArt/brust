# Loaders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Routes can declare `loader: (ctx) => Promise<unknown>` that runs in the Bun Worker before `renderToString`. The loader's resolved value becomes the component's `data` prop. Loader exceptions flow into the same try/catch that wraps render — caught by `errorBoundary` if declared.

**Architecture:** No wire-protocol changes. Loader runs entirely worker-side inside `makeRenderer`: parse envelope → look up route → if `route.loader` is set, `await route.loader({ params, path })` → render with `{ params, path, data }`. The cache (Plan LRU Cache) sits at the Rust HTTP layer downstream of the worker — it sees only the rendered bytes, so cache key + TTL work uniformly whether or not a loader ran.

**Tech Stack:** TypeScript-only change. No Rust changes, no new dependencies.

**Spec source:** `architecture.md` SRouting "Designed but not yet built" list lists `loader: async (req, params) => {...}` as the next deferred follow-up. This plan ships the loader piece without `req` (only `params` + `path`); `req` carrying cookies/headers lands with the Middleware Header-Mutation plan.

---

## Pre-flight: scope decisions

- **Loader context shape:** `{ params: Record<string, string>; path: string }`. Identical to `RouteContext` today. Future expansion (cookies, headers, search params) lands with Middleware.
- **`data` placement:** added as a third field on `RouteContext` (alongside `params` and `path`), typed as `data?: unknown` since loaders can return anything.
- **No loader → no `data` prop:** components without a loader receive `data: undefined`. Components with a loader receive whatever the loader resolved.
- **Loader exception:** caught by the same `try/catch` in `makeRenderer` that already catches render exceptions. `errorBoundary` (if declared) handles both. Without `errorBoundary`, the exception propagates to Rust → HTTP 500 via the existing `Err(e) => render error: {msg}` branch.
- **Cache interaction:** unchanged. The cache stores rendered HTML bytes, which already reflect whatever the loader produced. A cached `cache-test` hit doesn't re-run the loader — it serves the cached bytes. Correct semantic for opt-in caching.

Locate `makeRenderer`. The current try block calls `renderToString(createElement(route.Component, { params, path }))`. Update it to also await the loader (if present) AND pass `data` into the component props. The full updated `makeRenderer`:

```typescript
export function makeRenderer(
  routes: Route[],
  view: Uint8Array,
): (envelopeJson: string) => Promise<number> {
  const encoder = new TextEncoder()
  const byId = new Map<number, Route>()
  routes.forEach((r, i) => byId.set(i, r))

  return async (envelopeJson: string): Promise<number> => {
    const call = JSON.parse(envelopeJson) as RouteCall
    const route = byId.get(call.route_id)
    if (!route) {
      console.error(`[brust] unknown route_id=${call.route_id} for path=${call.path}`)
      return 0
    }

    let html: string
    let status = 200
    try {
      // Loader runs first (if declared). Exceptions flow into the same catch
      // as render exceptions — errorBoundary handles both uniformly.
      const data = route.loader
        ? await route.loader({ params: call.params, path: call.path })
        : undefined
      html = renderToString(
        createElement(route.Component, { params: call.params, path: call.path, data }),
      )
    } catch (renderErr) {
      if (!route.errorBoundary) throw renderErr
      const boundary: ReactNode = createElement(route.errorBoundary, {
        error: renderErr instanceof Error ? renderErr : new Error(String(renderErr)),
      })
      html = renderToString(boundary as any)
      status = 500
    }

    // Wire format: [status_u16_BE][body bytes].
    view[0] = (status >> 8) & 0xff
    view[1] = status & 0xff
    const bodyView = view.subarray(2)
    const { written } = encoder.encodeInto(html, bodyView)
    if (written === undefined) return 0
    return written + 2
  }
}
```

Three changes vs the prior version:
1. The `try` block now awaits `route.loader(ctx)` (if defined) before calling `renderToString`.
2. The `createElement(route.Component, ...)` call gains a third prop: `data`.
3. The comment on the try block notes that loader exceptions are caught by the same path.

## Risks / caveats

1. **Loader is per-request, not memoized.** Two requests to `/blog/foo` run the loader twice unless cached at the Rust HTTP layer. For the example, the loader is a no-IO synthesis — cost is negligible. For real IO loaders, users opt into the LRU Cache.
2. **Loader runs on every cache miss.** When `cache: { ttl_seconds: 60 }` is set, the first hit runs the loader + renders; the next 60 seconds of hits return cached bytes without invoking the loader. This is the right semantic — the cache key already includes path + vary, so the cached bytes reflect the loader's output for that key.
3. **`data` is `unknown` by default.** Components that don't narrow via the second `RouteContext` type parameter access `data: unknown` and must do their own type-checking. Acceptable trade-off vs. forcing every component to declare a `Data` type when most don't use loader data.
4. **Loader errors get HTTP 500 only via errorBoundary.** Without `errorBoundary`, the loader's thrown error propagates as the rejected promise → the existing `Err(e) => render error: {msg}` branch in `handle_conn` → HTTP 500 with `text/plain` body. Documented in SRouting "Designed but not yet built" follow-ups.

## Out of scope

- Loader `req` carrying cookies, headers, search params. Middleware Header-Mutation plan.
- Client-side loader invocation on navigation (hydration story). Navigation plan.
- Loader streaming / progressive rendering. HTML Streaming plan.
- Per-route loader caching independent of the response cache. No use case yet; revisit if it surfaces.
- Type-checking the loader's return matching the component's `Data` parameter at the route-table call site. TypeScript's inference handles this in practice; explicit enforcement would need a more elaborate `defineRoutes` generic.
