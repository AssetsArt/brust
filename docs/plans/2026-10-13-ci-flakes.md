# CI flakes after the gaps round: two lanes (F127, F128)

owner: 22499151-e133-4508-b358-d7fa4d2851c3 (Detoro) · authority: in-loop · base: v2 @cba919a · flow: lane → PR → CI → lead merges · ledger rows: F127 (`flake-413-chunked`), F128 (`flake-listening-on`) · blackboard: `flakes:v2` entries #4 and #5 · model: `2026-10-13-hydrate-flake.md` (R26.1–R26.4 apply as R28.x below)

## Why

The full CI run on v2 @cba919a (run 38383208039, 2026-10-13) failed on two tests that had only ever failed on developer machines before:

| Job | Test | Symptom |
|---|---|---|
| rust | `crates/brust-server/tests/actions.rs::chunked_body_over_cap_is_413` | panic at `tests/common/mod.rs:364:65`: `sender.send_request(...).await.unwrap()` errored while the helper was still streaming 300 KB of chunks; the server had already answered 413 and closed the connection (`crates/brust-core/src/actions.rs:67` → `body::error_413`). |
| rust (rerun 1 of the same run) | `crates/brust-server/tests/busy.rs::no_workers_is_503_immediately` | panic at `busy.rs:52:5` on the re-run of the same job: a second timing-sensitive brust-server test; the runner was loaded (the first attempt failed on the 413 test only). |
| server | `tests/server/cache-adapter.test.ts` `boot()` (line 42) | `TypeError: null is not an object` on `/listening on (\S+)/.exec(r.log())[1]`: the helper waited for `[brust] ready` and then expected `listening on` to be in the log already. Second CI hit (first: #171 run 38365810806). |

Both are races in test harness assumptions, not in the behaviour under test, but each lane must prove that, not assume it (R28.3).

## Rulings

- **R28.1 No blind retry, no blind timeout.** A `retry` wrapper or a longer wait without a named cause is rejected at review.
- **R28.2 The next failure must explain itself.** Each fixed test reports, on failure, what it saw: the full server log so far (listening-on), or the client error and how many chunks were sent (413).
- **R28.3 Fix at the source, prove the layer.** The lane states, with evidence, whether the race is in the test helper or in the product, and fixes it there. For the 413 case: if the server closes before reading the request, say whether HTTP/1.1 clients in the wild (browsers, `fetch`) see a reset instead of the 413 — if they can, the fix is in the server (read-and-discard up to a bound, or `Connection: close` + a graceful close after the response is flushed), not in the test. For the listening-on case: `listening on` is printed by the Rust server and `[brust] ready` by `packages/brust/src/run.ts:183` (Bun), two writers to the same stdout; say why the order can flip and whether `run.ts` should print `ready` only after the bound address is known.
- **R28.4 Evidence of green.** Two green `ci.yml` runs on the final head (PR run + one `workflow_dispatch`), ids in the ledger row; a local reproduction under load if one can be found (say how).

Both lanes are independent of each other and of the alpha.4 publish; they run after it.

**Amendment 2026-10-13 (ruling on Mellow's record 1, lane flake-listening-on @5ca5b43):** the cause was in the product, not the harness — the Rust server printed `listening on` without flushing before the Bun side could print `ready` — so the fix lives in `crates/brust-server/src/{config.rs,server/mod.rs}` and `crates/brust-napi/src/server.rs` (print + flush, then set `announced`; `untilReady` waits for it). That is R28.3 applied; the boundary is extended to those three files for this lane. The boot-order test stays a probabilistic guard (knock2 reproduced the race 3/120 before the fix).

**Amendment 2026-10-13 (ruling on Tiësto's challenge f5342a10, lane flake-413-chunked):** the race is in the product. On unmodified v2 a raw client sending a 300 KiB chunked body over a 256 KiB cap got 44/200 write errors and, with a concurrent reader, 130/200 connection resets after the 413 head: the handler answers 413 and hyper closes with the rest of the request unread, so the kernel resets. Fix in `crates/brust-server/src/host.rs` `read_capped`: drain a refused body up to a size cap and a wall-clock cap (1 MiB / 2 s as proposed) before returning `TooLarge`, and the 413 carries `Connection: close`; the boundary is extended to `host.rs` (`read_capped` and its constants) plus the tests. Review condition: both drain bounds hold (denial-of-service angle), and `docs/actions.md`'s body-cap paragraph states the drain bound.
