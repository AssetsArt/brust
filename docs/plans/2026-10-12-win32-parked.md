## 1. Goal
- `@brust/native-win32-x64-msvc` and `@brust/native-win32-arm64-msvc` exist as `npm/win32-x64-msvc/` and `npm/win32-arm64-msvc/`. `release.yml` builds both (`brust.win32-*.node`) and publishes them next to the six existing ones. The packed `@brust/core` lists **8** `@brust/native-*` optional dependencies.
- On Windows x64, `bun create @brust/app` → `bun install` → `brust build` → `brust start` works. A page renders, and an action answers through Rust. `packages/create-app/test/scaffold.test.ts` proves this on `windows-latest`.
- `ci.yml` gains two blocking Windows jobs (R5). They build the addon, run `cargo test -p brust-server -p brust-jinja`, run the compiler hardening tests, run the `packages/brust` unit + e2e set (the same files as the Linux `server` job, ci.yml:120-129), and run the create-app unit + scaffold tests.
- Build output does not depend on the build OS: component ids, `server_only` matching and `dist/index.js` all use `/`-relative paths (R8).
- On Windows, `brust start` drains on Ctrl+C (SIGINT) and Ctrl+Break (SIGBREAK). Linux and macOS behave exactly as before.
- Linux and macOS are byte-identical in behaviour. The only Rust change they see is the move of `rustls`/`tokio-rustls` into target tables (same features, same aws-lc provider).

## 2. Rulings requested
**R1 — TLS crypto provider on Windows.** Facts: `rustls 0.23.45` → `aws-lc-rs 1.18.1` → `aws-lc-sys 0.45.0` (deps `cc`, `cmake`; Cargo.lock:66-86, 1933-1946). `tls.rs:53` installs `rustls::crypto::aws_lc_rs::default_provider()`. `ring 0.17.14` is already in the lock through `rustls-webpki` (Cargo.lock:1887). **TLS cannot be reached from `@brust/core`**: napi `StartOptions` has no TLS field (`packages/brust/src/native.ts:18-34`, and no `tls` anywhere in `crates/brust-napi/src`), and `config.rs:192` defaults `tls: None`. So the provider matters only for the Rust API and its tests (`tls.rs:150-227`).

*Default (b):* use ring on Windows only. In `crates/brust-server/Cargo.toml`, move lines 31-32 into `[target.'cfg(not(windows))'.dependencies]` unchanged (`tokio-rustls = "0.26"`, `rustls = "0.23"`). Add `[target.'cfg(windows)'.dependencies] tokio-rustls = { version = "0.26", default-features = false, features = ["logging", "tls12", "ring"] }` and `rustls = { version = "0.23", default-features = false, features = ["ring", "std", "tls12", "logging"] }`. Then `tls.rs:53` picks `aws_lc_rs` under `#[cfg(not(windows))]` and `ring` under `#[cfg(windows)]`. Both crates must leave `[dependencies]` entirely: under resolver 3, a default-features entry there would unify aws-lc back in on Windows. ring needs no NASM on x64. On aarch64-msvc it needs `clang`, which ships with windows-latest (LLVM). The release leg checks for it (Task 8).

*Alternatives:*
- (a) Keep aws-lc on Windows. This needs CMake plus NASM (x64) and clang-cl (arm64), so more CI installs, and how aws-lc-sys 0.45 builds on aarch64-msvc is unverified.
- (c) ring everywhere. Simplest, but it changes the Linux/macOS provider, which the lead rejected.
- (d) Remove TLS from the build on Windows behind a cfg. That creates two API shapes.

**R2 — Bun-crate externs that the MSVC linker cannot resolve.** Bun's crates (44 git crates, among them `bun_sys`, `bun_libuv_sys`, `bun_windows_sys`, `bun_crash_handler`) declare C symbols that Bun's own C++ or libuv normally provides. They ship no build.rs. On Linux and macOS, a cdylib may leave symbols undefined (glibc resolves them lazily; napi-build passes `-undefined dynamic_lookup` on macOS), and executables drop unreachable callers with `--gc-sections`/`-dead_strip`. MSVC `link.exe` fails with LNK2019/LNK2001 when it cannot resolve a symbol, and a debug `build:debug` has no LTO to drop dead callers. There is precedent: `crates/brust-napi/src/stubs.rs:1-16` (`__bun_run_file_poll`, abort on call) and `crates/brust-compiler/src/parse/stubs/extra.rs:88-104` (Linux-only `Bun__linux_trace_*`).

*Default (a):* add `crates/brust-compiler/src/parse/stubs/windows.rs` (`#[cfg(windows)] pub(super) mod windows;` in `stubs/mod.rs`). It gets one `#[unsafe(no_mangle)]` stub per symbol the linker names. Each stub calls `eprintln!("brust: <sym> reached (Bun native side not linked)")` and then `std::process::abort()`. Where an "unavailable" return is correct (like `Bun__linux_trace_init` → 0), return that instead. The signatures are copied from the `extern` declaration in the Bun crate at rev 620b50f. Use this when the linker names **≤ 60** symbols.

*Alternative (b):* add `/FORCE:UNRESOLVED` for msvc in `crates/brust-napi/build.rs` (and in a `.cargo/config.toml` `[target.'cfg(all(windows, target_env = "msvc"))'] rustflags` entry for test executables). This matches the Linux lazy-binding model, but a call that hits a missing symbol crashes with an access violation instead of a named abort. If the linker names more than 60 symbols, the implementer stops and files a challenge with the list.

**R3 — a Bun crate that fails to *compile* (not link) on Windows.** *Default:* stop and `conclave task challenge` with the rustc errors. Do not patch inside the Bun crates. *Alternative:* vendor-patch the crate the way `vendor/bun_react_compiler` is patched (`Cargo.toml [patch."https://github.com/oven-sh/bun"]`), when the patch is ≤ 20 lines.

**R4 — how arm64 is built.** The premise is wrong: GitHub *does* host a Windows arm64 runner, `windows-11-arm`, and it is free for public repos (`gh api repos/AssetsArt/brust` → `"visibility":"public"`).

*Default:* cross-compile on `windows-latest` with `--target aarch64-pc-windows-msvc` and **no** `--cross-compile` flag. This is the napi-rs package-template layout. The MSVC ARM64 build tools and LLVM clang are on that image. `--cross-compile` would switch to cargo-xwin, which is only needed off Windows.

*Alternative:* build natively on `windows-11-arm`. That image's toolset (VS ARM64 tools, rustup) is unverified, but it would let a later lane run an arm64 smoke. Either way, this lane runs **no** arm64 binary in CI. This is a known gap and goes in the READY note.

**R5 — CI shape and budget.**

*Default:* two parallel, **blocking** jobs on `windows-latest`, each with `timeout-minutes: 60`:
- `windows-rust` runs `cargo test -p brust-server -p brust-jinja` plus `cargo test -p brust-compiler --test hardening --test parse`. It does not link the addon. Estimate: ~12 min warm, ~30 min cold.
- `windows` runs `build:debug`, the packages/brust test set, and the create-app unit + scaffold tests. Estimate: ~18 min warm, ~40 min cold. The cold cost comes from compiling the Bun crates; the Linux `server` job needs 4.5 min (napi test) plus 4 min (build:debug) warm (run of 2026-10-12 01:33), and Windows runs about 1.5-2× slower.

A single combined job would take ~25-30 min warm, which breaks the ~20-minute budget. Both jobs check out with `core.autocrlf false` (all 1066 text files are LF in the index; with CRLF, byte-exact fixtures break) and `core.longpaths true` (cargo's checkout of the oven-sh/bun repo).

There is no clippy on Windows. Its cost is ~3 min. The cfg(windows) code is small (Tasks 3-4), and the reviewer reads it.

*Alternative:* make the e2e/scaffold step `continue-on-error` for the first iteration. Only if it proves flaky, which needs a new ruling.

**R7 — shutdown signals on Windows.** *Default:* add `shutdownSignals(platform)` in `run.ts`. It returns `[['SIGINT',130],['SIGTERM',143]]`, plus `['SIGBREAK',149]` on win32 (128+21). The `SIGTERM` listener stays on every platform; Node documents it as harmless on Windows, where it never fires. *Alternative:* also drain on `SIGHUP` on win32 (console window closed; Windows kills the process ~10 s later).

**R8 — where paths get normalised.** *Default:* normalise to POSIX at the TS seam with a new `packages/brust/src/build/paths.ts`, so component ids (`component_id` hashes the path string, `crates/brust-compiler/src/ir/mod.rs:136-155`) are the same on every OS. This also fixes child-import resolution: `crates/brust-compiler/src/analyze/modules.rs:177` uses `parent.rfind('/')`, so a Windows `routes\Home.tsx` would resolve `./Card` against the app root. *Alternative:* teach the Rust compiler to accept `\`. That touches ids and resolution in Rust, and ids would still differ by OS.

**R9 — CRLF sources (Windows users' editors).** *Default:* add one platform-neutral test to `napi-compile.test.ts`. It compiles a CRLF copy of `tests/fixtures/theme-toggle/input.tsx` (written to a temp root) and asserts ids, `jinja` and `clientJs` equal to the LF compile. If it fails, stop and challenge: that would be a compiler bug outside this lane. *Alternative:* skip the test and record a risk.

### Task 3 — stack bounds on Windows (`crates/brust-compiler/src/parse/mod.rs`)
Today non-macOS/non-Linux falls to `stack_bottom() -> None` (`mod.rs:86-92`). With that, `ensure_stack_limit` (`:43-55`) hands Bun's recursion guard only 1 MiB of the 256 MiB compiler thread, and deep JSX gets refused.
- [ ] Change the fallback cfg to `not(any(target_os = "macos", target_os = "linux", windows))`. Add the following. It needs no new crate, and `kernel32` is already linked:
```rust
#[cfg(all(feature = "bun-stubs", windows))]
fn stack_bottom() -> Option<usize> {
    #[link(name = "kernel32")]
    unsafe extern "system" { fn GetCurrentThreadStackLimits(low: *mut usize, high: *mut usize); }
    let (mut low, mut high) = (0usize, 0usize);
    // SAFETY: writes the calling thread's own reserved stack range (Windows 8+).
    unsafe { GetCurrentThreadStackLimits(&mut low, &mut high) };
    (low != 0 && low < high).then_some(low) // None → the existing 1 MiB fallback
}
```

## 7. Risk ledger
- **The MSVC link (R2) is the long pole.** Every iteration is a ~30-40 min cold CI run. The cache key is shared after the first run. Sign it is breaking: `LNK2019 unresolved external symbol` in `build:debug`. Stop rule: after 3 dispatches with new symbols each time, challenge with the cumulative list.
- **Cargo's checkout of the oven-sh/bun git dep can hit MAX_PATH.** The sign is `path too long` / `failed to checkout`. Remedy: `core.longpaths true` (already in), plus `CARGO_NET_GIT_FETCH_WITH_CLI: "true"` in the job env.
- **The loader could pick gnu.** `native/index.js:120` keys on Bun's `process.config.variables`. The Task 2 print rules this out. Sign: `Cannot find module './brust.win32-x64-gnu.node'`.
- **`sourceOf` keys could miss on Windows.** The `bundle.ts` `sourceOf.get(a.importer)` lookup relies on Bun's importer string equalling `realpathSync(file)` (`stage()`, bundle.ts:264-267). Sign: `Could not resolve "./…"` from `.stage/` in the e2e build. Remedy: normalise keys with `toLowerCase()` + `\`→`/` on win32 on both sides. This is in boundary and must be written down in the READY note.
- **Rename races during build.** The `renameSync(dist, old)` swap (`index.ts:127-133`) can throw EPERM/EBUSY if Defender or a live `brust start` holds `dist/`. Sign: a flaky `brust build` in scaffold. Remedy is a separate ruling; do not add retries silently.
- **Timer resolution.** Windows timers tick at 15.6 ms, which can trip tight timing asserts in brust-server tests. R6 caps the ignores.
- **arm64 is built but never executed in CI (R4).** The first real arm64 run will be a user's. Say this in the READY note.
- **Linux/macOS regression from the Cargo.toml move.** Sign: `cargo tree -p brust-server -e features | grep aws-lc` empty on macOS. It must still list aws-lc-rs.
