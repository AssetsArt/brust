# L27 ci-speed: one addon build per run, no duplicated gates, content-keyed Rust cache (F124)

owner: 22499151-e133-4508-b358-d7fa4d2851c3 (Detoro) · authority: in-loop · base: v2 @ad6d354 · flow: lane → PR → CI → lead merges · ledger row: F124 (`docs/plans/m1a-followups.md`) · blackboard: `ci:no-manual-dispatch-on-prs`

## Why

The human asked on 2026-10-13 whether GitHub Actions can be made faster ("แล้ว github actions ทำให้เร็วขึ้นได้ไหม"). A green PR run takes 12–13 minutes wall-clock and about 43 runner-minutes. Measured on run 38360524514 (lane `external-island` @d9b8836, all jobs green):

| Job | Wall-clock | Where the time goes |
|---|---|---|
| server | 12m 48s | `cargo clippy -p brust-napi && cargo test -p brust-napi` 5m 38s; `bun run build:debug` 4m 18s; cargo cache restore 68s; the actual test steps total about 2 minutes |
| rust | 11m 23s | `cargo build --workspace` 5m 19s, then `cargo test --workspace --exclude bun_react_compiler` 3m 25s; cache save 56s |
| cf | 10m 42s | `bun run build:debug` 4m 32s; `cargo install worker-build` 1m 57s although a `worker-build-Linux-0.8.7` cache entry exists; wasm build 1m 23s; e2e 2m 7s |
| battery | 4m 15s | addon build again |
| browser | 4m 21s | addon build again |
| runtime-dom | 10s | — |

Three facts explain it:

1. **The addon is compiled four times per run** (server, cf, battery, browser each run `cd packages/brust && bun run build:debug`), and the rust job compiles the same crates a fifth time.
2. **The server job duplicates the rust job.** `cargo clippy -p brust-napi` is already in the rust job's clippy line (`ci.yml` line 39 lists `-p brust-napi`), and `cargo test --workspace` already runs the brust-napi tests.
3. **The cargo cache cannot keep `vendor/bun_react_compiler` warm.** The cache key is `hashFiles('Cargo.lock', 'rust-toolchain.toml')`, which covers registry and git dependencies. `vendor/bun_react_compiler` is a workspace path crate, and cargo fingerprints path crates by file mtime; a fresh checkout gives every file a new mtime, so the largest crate in the graph is recompiled in every job of every run even on a cache hit. (The cache entries are 0.7–3.1 GB each, so the restore and save steps cost another 1–2 minutes per job.)

A second problem, already fixed on the lead's side: a push to a PR branch triggers `ci.yml` by itself, and the lead's helper also dispatched the workflow manually; the two runs sit in different concurrency groups (`ci-${{ github.head_ref || github.ref }}`), so both ran. Four of the eight runs on the 2026-10-13 14:39 screenshot were duplicates. Blackboard `ci:no-manual-dispatch-on-prs` records the rule; this lane does not need to change the trigger.

## Rulings

- **R27.1 Same gates, fewer runs of them.** Every command that is a check today still runs somewhere in the workflow after this lane; the only removals are exact duplicates named in this plan. The PR description lists each removed line and the surviving line that covers it.
- **R27.2 One addon build per run.** A new `addon` job builds `packages/brust/native` once and publishes it as a workflow artifact; `server`, `cf`, `battery` and `browser` download it and do not run `bun run build:debug`. The artifact is the whole `packages/brust/native` directory (`brust.linux-x64-gnu.node`, `index.js`, `index.d.ts`; `native/.gitignore` is the only tracked file there) so the package's `./native` export works unchanged. All five jobs stay on `ubuntu-latest` (same libc, same arch), which is what makes the artifact portable between them.
- **R27.3 Content-keyed Rust compile cache.** Jobs that compile Rust (`rust`, `addon`, `cf`) run `sccache` with the GitHub Actions cache backend (`mozilla-actions/sccache-action`, `SCCACHE_GHA_ENABLED=true`, `RUSTC_WRAPPER=sccache`). sccache keys on source content and arguments, so the vendored crate hits the cache when its files are unchanged, regardless of mtime. The `actions/cache` step keeps `~/.cargo/registry` and `~/.cargo/git`; whether `target` stays in it is decided by measurement (see Acceptance), not by taste: keep it only if dropping it makes the run slower.
- **R27.4 Measure before and after.** The ledger row carries wall-clock and total runner-minutes for one run before and two runs after, from the run's Usage page, with run ids. A change that does not show up in those numbers is reverted inside the lane.
- **R27.5 No new secrets, no new runners.** GitHub-hosted `ubuntu-latest` only; sccache uses the Actions cache that the repo already has (10 GB limit; current usage 9.3 GB across 10 entries, which this lane trims by dropping the per-job `target` caches if R27.3's measurement allows).

## Changes, in order

1. **`addon` job.** Checkout, toolchain (`nightly-2026-09-15`, `rust-src`), bun canary, the cargo cache step, `bun install --frozen-lockfile`, `cd packages/brust && bun run build:debug`, then `actions/upload-artifact@v4` with `name: addon-linux-x64`, `path: packages/brust/native`, `retention-days: 1`, `if-no-files-found: error`.
2. **`server`, `cf`, `battery`, `browser`.** Add `needs: addon`, replace their `bun run build:debug` step with `actions/download-artifact@v4` (`name: addon-linux-x64`, `path: packages/brust/native`). Remove the cargo cache step from the three jobs that no longer compile Rust (`server`, `battery`, `browser`); `cf` keeps it for the wasm build. `server` also drops `cargo clippy -p brust-napi --no-deps -- -D warnings && cargo test -p brust-napi` and the Rust toolchain step if nothing else in the job needs cargo (check `tests/server/*` and `packages/cache-redis` for cargo invocations first; if one exists, keep the toolchain and say which).
3. **`rust` job.** Drop `cargo build --workspace`; `cargo test --workspace --exclude bun_react_compiler` builds what it tests, and the invariant steps (`cargo tree …`) need no build. Keep fmt, the three `cargo tree` invariants, clippy for every crate, the wasm checks, and `bun build --no-bundle scripts/bun-codegen.ts`.
4. **sccache** in `rust`, `addon`, `cf` per R27.3. First run after the change is a cold cache; the second run is the one to measure.
5. **cf `worker-build`.** Find out why `cargo install worker-build` ran for 1m 57s with a `worker-build-Linux-0.8.7` cache entry present (the `actions/cache` step reported 0s, so either the key missed or `worker-build --version` does not print the bare version and the `grep -qF` fails). Fix whichever it is; the step must be a no-op on a warm cache.
6. **Trigger and concurrency** stay as they are (PR runs + `workflow_dispatch`, cancel-in-progress per head ref). Do not add `push:` triggers.

## Acceptance

- The PR's own runs: two consecutive green runs on the final head with `total duration` ≤ 8 minutes on the second (warm sccache) and total runner-minutes ≤ 25 (today: 43). Numbers and run ids in the F124 row.
- `grep -c 'build:debug' .github/workflows/ci.yml` is 1 (the `addon` job).
- A diff of every `run:` line before and after, in the PR description, showing that each removed line is one of: the three duplicate `build:debug` steps, the server job's `cargo clippy/test -p brust-napi`, the rust job's `cargo build --workspace`. Nothing else is removed.
- `docs/` mention of CI gates (`docs/plans/release-*.md` or wherever `release.yml` is told to mirror `ci.yml`) updated if it lists the removed commands; the release skill's mirror list (`.claude/skills/release/SKILL.md`) is NOT edited by this lane: it mirrors gates, not job layout, and the gates are unchanged.
- Ledger row F124 DONE with the PR number.

## Boundary

`.github/workflows/ci.yml`, `docs/plans/m1a-followups.md` (row F124), `docs/ci.md` if it exists. No change under `packages/`, `crates/`, `tests/`.

## Risks

- `download-artifact` into `packages/brust/native` must not clobber the tracked `native/.gitignore`; download-artifact writes only the files it holds, and the `.gitignore` is not in the artifact if `upload-artifact` honours it (it does not: upload-artifact uploads what the path matches). Either way `git status` must stay clean after download; add a step that asserts it.
- If the `addon` job fails, four jobs are skipped and the run is red in under 5 minutes, which is the right outcome.
- sccache-action pins a version; choose the latest release at least two weeks old and record it in the F124 row.
