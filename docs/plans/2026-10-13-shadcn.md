# P2 shadcn/ui on brust: as much static and native as possible, as few React islands as possible (F138)

owner: 22499151-e133-4508-b358-d7fa4d2851c3 (Detoro) · authority: in-loop · base: main @60e2a13f · flow: lane → PR → CI → lead merges · ledger row: F138 (one row per lane: F138a, F138b, …) · depends on: L32 `tailwind-compiler` (F135) for anything that builds shadcn's CSS

## Why

Human order, 2026-10-13: "ทำ shadcn/ui คือทำให้ support native, static ให้เยอะที่สุด หรือทั้งหมดนะ ให้กลายเป็น react island ได้น้อยเท่าไหร่ยิ่งดี". A user copies shadcn/ui components into a brust app (the shadcn CLI writes `components/ui/*.tsx` + `lib/utils.ts`) and gets static HTML or a native chunk for each of them; a React island only where nothing else can behave the same.

What stands in the way today (docs/react-coverage.md, 145 rows): spread props onto hosts and components fall back (`a-spread-host`, `b-spread-child`: F31 `fallback:spread-props`); `createContext` / `useContext` fall back (`d-createcontext`, `c-usecontext`); `forwardRef` falls back (`b-forwardref`); every external component (Radix primitives) is an island. shadcn components are built from exactly these: `function Button({ className, variant, size, asChild = false, ...props }: React.ComponentProps<"button"> & VariantProps<typeof buttonVariants>)` → `<Comp data-slot="button" className={cn(buttonVariants({ variant, size, className }))} {...props} />`, with `cn` = `twMerge(clsx(...))`, `cva` variants, `Slot` for `asChild`, and Radix primitives (`radix-ui`) for everything interactive.

## Rulings

- **R34.1 Measure first, then build (S0).** No compiler or runtime work for shadcn starts before the survey lands: it is the scoreboard every later lane moves.
- **R34.2 The scoreboard is generated.** `docs/shadcn-coverage.md` is generated by a script (like `bun run battery` → `docs/react-coverage.md`): one row per shadcn component and per realistic usage (e.g. `button` default, `button asChild` with a link, `dialog` open/close), observed tier, fallback reasons, island count on the page, client JS bytes. CI fails on a diff (same rule as the battery). The shadcn version is pinned (exact registry version recorded in the doc header); upgrading it is a deliberate PR.
- **R34.3 Same behaviour or no change.** A component may leave the React tier only if it renders the same HTML (same `data-slot`, `data-state`, `aria-*`, class strings after `cn`) and behaves the same for the user (keyboard, focus, open/close, form values) as the React version. Each lane proves it against the React rendering of the same usage (the survey keeps a React-tier reference build for comparison: HTML diff + a Playwright behaviour script per interactive component).
- **R34.4 Order of attack (amended by the lead after S0 with the measured counts).** (S1) compiler patterns shadcn's presentational components need: rest-props spread of a known shape onto host elements and components (F31), `cn(...)`/`clsx`/`twMerge` and `cva(...)` class computation (fold at compile time when the inputs are literal at the call site; otherwise a server precompute, never a client bundle of tailwind-merge for a static component), `asChild` + `Slot` with a literal child, `data-slot` passthrough, `React.ComponentProps<…>` typing only; (S2) context: `createContext` + `useContext` where provider and consumers are in the same compiled tree (shadcn's own context components: Form field, ToggleGroup, Carousel, Sidebar), as a native store; (S3) native Radix: brust ships native-tier implementations of the Radix primitives shadcn uses (same DOM contract: `data-state`, `aria-*`, roving focus, dismiss on Escape/outside click, focus trap for modal ones; overlays on the platform's `<dialog>` / Popover API), selected at compile time when an app imports `radix-ui` / `@radix-ui/react-*` within the supported prop subset; anything outside the subset stays the real Radix in an island. Priority by S0 frequency × how often apps use it (Dialog, DropdownMenu, Tabs, Accordion, Popover, Tooltip, Select, Checkbox, Switch, RadioGroup, Collapsible, Label, Separator, Avatar, Progress, Slider, Toggle(-Group), ScrollArea, HoverCard, Sheet, AlertDialog, NavigationMenu, ContextMenu, Menubar).
- **R34.5 Honest leftovers.** Components that wrap a third-party React library (Calendar → react-day-picker, Chart → recharts, Carousel → embla, Command → cmdk, Form → react-hook-form, Sonner, Drawer → vaul, Resizable, Input OTP) stay React islands unless S0 shows a cheap path; the coverage doc says so per row. No hand-written brust fork of a shadcn component: the user's copied source must compile as written.
- **R34.6 Docs.** A docs-site page "shadcn/ui" (install with the shadcn CLI into a brust app, which components are static/native/react and why, linking the generated table); `docs/shadcn.md` in the repo. Added when S1 lands, updated per lane.

## Amendment 2026-10-13 (human, overnight): compile external libraries, do not replace them

Human: "คือแก้ compiler ให้ support การใช้ lib ข้างนอกด้วยไปเลย อันที่ซับซ้อนจริงๆค่อยกลายเป็น react island" — the compiler itself learns to compile components that come from packages (Radix and the other libraries shadcn imports), the same way it compiles the app's own files; only what is genuinely too complex stays a React island.

- **R34.7 (replaces R34.4 S3).** Today an imported component from `node_modules` is an island by rule (`fallback:external-component`). That rule goes: the compiler follows imports into packages (their published ESM/JS, plus `.d.ts` only for types) and analyses each component like app code. A package component lands static or native when every pattern it uses is supported, and is an island only when its own analysis says so (with the reason in the coverage table). brust does NOT ship its own replacement implementations of Radix primitives; the "native Radix shim" idea is withdrawn unless S0+S1 data show a specific primitive cannot be compiled and the lead rules a narrow exception.
- **R34.8 S0 measures libraries too.** For every package the fixture imports (`radix-ui` / `@radix-ui/react-*`, `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react`, `react-day-picker`, `recharts`, `embla-carousel-react`, `cmdk`, `vaul`, `sonner`, `react-hook-form`, `input-otp`, `react-resizable-panels`, …), the survey also runs the compiler over the package's component modules as if they were app code (a scripted analysis; no product change) and records per component the blocking patterns (`fallback:*` codes and the construct, e.g. `useContext`, `useLayoutEffect`, `forwardRef`, `composeRefs`, `createPortal`, `useSyncExternalStore`, `React.Children`, `cloneElement`). The ranked list combines app-level and library-level blockers; S1+ lanes are cut from it.
- **R34.9 Likely S1+ patterns (to be confirmed by S0):** rest-props spread (F31), `forwardRef` and ref composition, `createContext`/`useContext`/`Provider` across the compiled tree (incl. across package boundaries), `useLayoutEffect`/`useEffect` with DOM refs, controllable state (`useControllableState`-style hooks are custom hooks: L5 inlining applies), `Slot`/`cloneElement` with a known child, `Children.only`/`Children.map` over literal children, `createPortal` into `document.body` (native: move the node on mount), `useId`. Each becomes a compiler lane with battery rows in `docs/react-coverage.md` AND moved rows in `docs/shadcn-coverage.md`.
- **R34.10 Safety stays.** Compiling a package must never change its behaviour: R34.3 (same HTML + same behaviour vs the React build) applies to every package component that leaves the island tier, and any construct the compiler cannot prove keeps the component an island (fail closed), exactly as for app code.

## S1.2 — lane `rest-props` (cut 2026-10-14 from the measured ranking: #1 `prop-pattern` 58 rows, #2 `spread-props` 58 rows)

Evidence: `docs/shadcn-coverage.md` after S1.1 (lead regeneration on #198). Both blockers come from shadcn's one signature: `function Button({ className, variant, size, asChild = false, ...props }: React.ComponentProps<"button"> & …) { return <Comp data-slot="button" className={cn(…)} {...props} /> }`. The compiler refuses `...rest` in the props pattern (`crates/brust-compiler/src/analyze/hooks.rs` `read_props`, `names.rs` NameTable: "nested patterns and `...rest` are a `prop-pattern` fallback") and refuses any JSX spread (`analyze/jsx.rs`: "spread props cannot be expanded by the template backend", F31).

- **R34.14 Rest in the props pattern.** `{ a, b = 1, ...rest }` (and `{ a: local, ...rest }`) is a supported props pattern: `rest` is the props object minus the named keys. Nested patterns and computed keys stay a fallback.
- **R34.15 Spread with React's semantics.** `<host {...x} attr=…/>` and `<Comp {...x} prop=…/>`: later wins, exactly as React (`className` before `{...props}` is overridden by `props.className`); `key` and `ref` are not props; `children` in a spread is the element's children unless JSX children are given. Two expansion paths, chosen by the compiler: (a) **known shape** — when the spread's keys are known at the call site (the common case: the child is inlined/linked with literal props at its use site, so `rest` is a literal object there), expand at compile time into ordinary attributes/props: the output is identical to hand-written attributes; (b) **unknown shape** — a runtime expansion in the template backend: a Rust-side attribute renderer that maps React names to HTML (`className`→`class`, `htmlFor`→`for`, `style` object→CSS text, boolean attributes, `data-*`/`aria-*` as given), escapes every value, VALIDATES every attribute name against the HTML attribute-name grammar (drops and warns on anything else), never prints `dangerouslySetInnerHTML`, `on*`, `ref`, `key`, `children`, or `x-*` (F94 reserved names). Function values (event handlers) reaching a host through a spread make the component native (bound as the existing function-prop path does) when the compiler can see them; when it cannot (unknown shape at runtime), a function value is dropped from the HTML exactly as React SSR does, and the component must already be native or React for it to work — the compiler keeps it on the tier that guarantees the handler is bound (fail closed: React tier if unprovable).
- **R34.16 Battery + scoreboard.** `a-spread-host` and `b-spread-child` leave the React tier; new battery rows: rest pattern, spread then override, override then spread, spread of `data-*`/`aria-*`/boolean/`style`, spread carrying an event handler (native), spread of an unknown-shape object (runtime path), hostile attribute names in a runtime spread (dropped + warned), `x-*` in a spread (dropped, F94). `docs/shadcn-coverage.md` regenerated: the rows whose only blockers were `prop-pattern`/`spread-props` move; the lane names them in its PR.
- **R34.17 Security review.** The runtime path (b) is an HTML output sink: the reviewer checks it like `html_raw` (inner-html lane) and F94; tests include attribute-name injection (`"onmouseover=alert(1) x"` as a key), value quoting, `javascript:` URLs in `href`/`src` through a spread (same url guard as hand-written attributes).

## S1.3 — lane `spread-handlers` (F141, after S1.2 merges; Dew)

- **R34.18 Parent-scope binding.** When a child that receives a function through its rest spread is otherwise static and unlinked, the parent hoists the forwarded function as its own member and the inline print emits the event binding (`x-on-<event>` to that member) on the child's element, which sits in the parent's scope: the output equals hand-written markup in the parent. The parent becomes native (it owns a handler); the child stays static. Covers shadcn `Button`, `Card`, `Badge`, … used with `onClick` and other `on*` props.
- **R34.19 Limits stated.** Linked/native children, handlers that close over the child's own state, and non-event function props (render props) stay fail-closed with their own codes; each is a battery row.
- **R34.20 Proof.** The S1.2 knownGap row flips to native; Chromium tests click a shadcn `Button` with `onClick` from a native parent, with the parent's state updating; `docs/shadcn-coverage.md` regenerated, rows named in the PR.
