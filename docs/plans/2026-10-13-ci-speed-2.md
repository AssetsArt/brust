# L27b ci-speed-2: make the Rust cache actually hit (F124, round 2)

## Why

Round 1 (#170) removed the duplicated gates and the double addon build, but R27.4's targets were not met. Measured on the two green runs at 2213a3d:

| Run | rust | addon | cf | server | battery | browser | runner-min (sum) | critical path |
|---|---|---|---|---|---|---|---|---|
| 38365337799 (cold) | 10.4m | 6.2m | 5.2m | 3.0m | 3.8m | 3.9m | ~33 | rust 10.4m |
| 38366677394 (warm) | 8.6m | 7.4m | 7.7m | 3.4m | 3.6m | 3.6m | ~35 | addon 7.4m + server 3.4m ≈ 11m |

Tiësto's reading of the logs (ci-speed task note): the warm run's sccache hit rate on Rust is 0–6 % (addon 1.6 %), and dropping `target` from `actions/cache` made the addon build slower than before round 1 (7.4m vs 4.3m). So round 1 traded a working-but-coarse cache for a fine-grained one that does not hit. The first-attempt failure of the cold run's server job was the F122 hydrate flake (fourth CI-only hit, all before #169 landed), not the CI change.

## Rulings

- **R27b.1 Diagnose before changing.** The first commit of the lane is one diagnostic PR run only: `SCCACHE_LOG=debug` (or `sccache=debug`) and `SCCACHE_ERROR_LOG` in the `addon` and `rust` jobs, `sccache --show-stats` already present. The task note states, with log lines, why the warm run missed: GHA cache key scope (the action's `SCCACHE_GHA_CACHE_TO`/`FROM` defaults and immutable-entry "already exists" behaviour when five jobs write the same key), hash inputs that differ between runs (absolute paths, `CARGO_*` env, `-C metadata`), or entries never saved. No other change ships in that commit.
- **R27b.2 Single writer per cache key.** Whatever cache survives (sccache GHA entries, `actions/cache` `target`), each key is written by exactly one job and read by the others; the key names the job (`cargo-<job>-<os>-<lockhash>`), and the restore uses the job's own key first, then the shared prefix.
- **R27b.3 Restore the `target` cache** per job (R27b.2 keys) unless the diagnostic shows sccache alone reaches ≥ 80 % Rust hits on a warm run; the addon build must get back to ≤ 4.5 minutes warm.
- **R27b.4 The vendored path crate.** Choose by measurement between (a) `git-restore-mtime` (set file mtimes from commit times before cargo runs, so cargo's mtime fingerprint of `vendor/bun_react_compiler` matches the cached `target`) and (b) sccache hits for it. (a) needs no sccache; if (a) makes the vendored crate "Fresh" in the warm run's cargo output, sccache may be dropped entirely (R27.3 is then satisfied by the restored `target` cache plus mtime restore, and the plan says so in the F124 round-2 paragraph).
- **R27b.5 Same gates** (R27.1 unchanged); no new secrets or runners (R27.5).

## Acceptance

- Two consecutive green PR runs on the final head; the second (warm) has `total duration` ≤ 8 minutes and runner-minutes ≤ 25; per-job minutes and the warm cache hit rate (or "Fresh" count) in the F124 row's round-2 paragraph with both run ids.
- `grep -c 'build:debug' .github/workflows/ci.yml` still 1; actionlint clean.
- If the targets are still not met after the fix, the row says what was reached and what remains, and the lane closes anyway (no third round without a new idea).
