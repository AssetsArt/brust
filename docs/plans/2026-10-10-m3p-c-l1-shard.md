# m3p-c-l1-shard — P4: an L1 HIT that takes no shared lock (sharded read front, lock-free route table, envelope after the L1 decision)
owner: 22499151-e133-4508-b358-d7fa4d2851c3 · authority: in-loop · base: m3p · escalation: lead Detoro via task challenge

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land lever P4 of the M3-P spec on lane `lane/m3p-c-l1-shard` (from `m3p` @ 42db1d1). After this lane an L1 HIT is `match` + `get` with no shared lock word written on the way: (1) `L1Cache` reads come from a sharded read front, with moka kept as the lifetime policy, like the job cache's front; (2) `RouteTable` is immutable after boot, so `match_path`/`compiled_cache_for` stop taking a `parking_lot::RwLock` on every request; (3) the request envelope (headers, cookies, decoded query) is built only after `l1_decision` says MISS/BYPASS, and a HIT allocates nothing for it. The output stays byte-identical. Probe **S** (`/types`, an L1 HIT) is the probe this lever is meant to move. **D** and **I** (`?nocache=1`, BYPASS: they never read L1) must not regress, and they gain only from (2) and from three allocations removed on every page request.

**Architecture:** There are four decisions, and each is backed by a number in "Evidence".
(a) **Front shape: copy the job cache's design, except for the shard lock.** The job cache (`cache/job_cache.rs:73-395`) keeps payloads in 64 `parking_lot::RwLock<HashMap>` shards. It stamps each entry with its own `expires_at` and an insert `generation`. moka holds only the policy part (ttl, tags, generation), and its eviction listener removes the front entry whose generation matches. Same-key writers serialize on a per-shard stripe `Mutex`. A front hit forwards to moka at most once per 100 ms per key, and the hit/miss counters are striped. That design works for the job cache because a page's lookups spread over many keys. S reads ONE key, so every tokio thread hits one shard's `RwLock` word. In the scratch test that design improves the hot key only from 3.08 µs to 1.99 µs per get under 8 threads. Readers that take `crossbeam_utils::sync::ShardedLock` lock only their own sub-lock, and the same lookup costs 83 ns under 8 threads (78 ns on 1 thread). `crossbeam-utils` 0.8.23 is already in `Cargo.lock` through moka, so no new crate is downloaded (ruling R-A). Everything else is copied from the job cache: generation, listener, stripes, touch and striped counters.
(b) **`get_with(&key, f)`, not `get → Arc`.** One shared `Arc` clone plus its drop costs about 610 ns under 8 threads, so the HIT response is built inside the read guard. A gzip that has not been made yet leaves the guard by moving a cloned `Arc` out, so writers never wait on a compression.
(c) **`RouteTable` without locks.** Nothing calls `install_with_config` after boot: the only callers are `from_manifest` and the tests. A plain `matchit::Router` costs 19 ns under 8 threads, against 1.47 µs under its `RwLock`. Path-param names can then borrow the table instead of being `to_string()`ed per request.
(d) **Lazy envelope.** `match_route` returns `RouteMatch { route_id, not_found, params }`. `l1_decision` decodes the query only when one exists and hands the decoded list on, and `RouteMatch::into_envelope` builds the identical `RouteEnvelope` on a MISS/BYPASS. `match_path` stays as a thin wrapper, so the existing routing tests keep their meaning.

**Tech Stack:** Rust nightly-2026-09-15, moka 0.12.16 (`sync::Cache`, `Expiry`, eviction listener, `remove`), `crossbeam_utils::sync::ShardedLock` 0.8.23, matchit 0.9.2, parking_lot 0.12, criterion 0.8 (`cargo bench -p brust-server --bench render`), Bun canary, `oha`.

## Review Focus

1. **Front ⊆ moka invariant and listener re-entry.** A front entry of generation G exists only while moka holds G or G's insert is in flight. Writers of one key (`insert`, `remove`) hold that key's stripe across "stamp generation, index, front write, moka write", and the front write guard is released BEFORE the moka call, because moka may run the listener inline inside `insert`/`remove`. The listener takes the tag-index `Mutex` and the shard's `ShardedLock::write` (each alone) and never a stripe or the gate. Lock order: gate → stripe → (index | front), each alone. Pinned by `concurrent_reinserts_leave_front_and_moka_agreeing`, `front_follows_moka_evictions_and_expiry`, the unchanged `reinsert_keeps_newer_entry_tag_indexed` and `invalidate_between_index_and_insert_is_not_lost`, and the stress test `invalidation_under_concurrent_hits_is_immediate`.
2. **Invalidation reaches the front synchronously.** `invalidate_tags`, `invalidate_path` and `clear` remove front entries before they return, rather than waiting for moka maintenance (today moka `invalidate`/`invalidate_entries_if` are lazy, but `get` already observes them). `invalidate_path` stops using `invalidate_entries_if` (and the builder drops `support_invalidation_closures`). It collects matching keys by scanning the front shards, then `remove`s each, and its returned count is the number of live (unexpired) matches, as moka's `iter()` counted. TTL is exact on read (`expires_at`), as in the job cache. Pinned by `invalidation_reaches_the_front_without_maintenance`, `ttl_is_exact_on_the_read_front`, the unchanged `invalidate_path_*`/`invalidate_tags_*`/`clear_*` tests, and `tests/server.rs::invalidate_by_tag_forces_miss`.
3. **Envelope byte-identity.** `into_envelope` produces the same `RequestEnvelope` (header order, cookies across headers, decoded search, params decoded with `decode_path_param`). `l1_decision` decodes the query with the SAME `decode_search` the envelope used, so the duplicate-name bypass and `query()` expressions see the same pairs. Pinned by the characterization test written on the unchanged tree (Task 1 Step 6), `match_route_into_envelope_equals_match_path`, and the existing `encoded_query_name_still_bypasses`, `encoded_query_value_matches_eq`, `duplicate_cookie_cannot_poison_l1`, `bypass_skips_l1_and_prefix_keys_it`.
4. **`get_with` closure discipline.** The closure runs under a shard read guard: it must not call into `L1Cache` (that would deadlock against a writer waiting on the same shard), must not `.await`, and must stay short. The HIT closure clones the header map and the body `Bytes`, or returns `Err(Arc)` for a first gzip. Pinned by `get_with_runs_the_closure_once_and_only_on_a_hit` and `tests/cache.rs::hit_answers_identity_and_gzip_from_one_entry` (the first gzip request goes down the `Err` path).
5. **Route table immutability.** `install_with_config` takes `&mut self`, and `Server.routes` is never mutated after `start`. Check with `grep -rn 'install_with_config' crates/` → only `routes.rs`.

Reading the table: every shared RMW on one hot cache line costs ~600-1,500 ns under contention. Today's HIT has four sources of them: two route-table `RwLock`s, moka plus the `Slot` clone, and the body `Bytes`/Content-Type refcounts. P4 removes the first three. The body `Bytes` clone is inherent (hyper takes an owned `Bytes`), and Content-Type is R-C. Expected HIT prelude under 8 threads: 3.46 µs → ~1.2 µs (≈ 0.96 µs with R-C), on a page that costs ~89 µs of host CPU per request at 112 k rps. So **S should gain about +1…4 %**: real, but close to the oha noise band. The hard acceptance is therefore criterion; oha S is reported with its Δ and must not fall below before.

/// Decoded query pairs (`url_decode`, `+` = space), in order, empty pairs skipped: the envelope's `search`
/// and what `l1_decision` keys and dedupes on — one function so both see the same pairs.
pub type Search<'a> = Vec<(std::borrow::Cow<'a, str>, std::borrow::Cow<'a, str>)>;
pub fn decode_search(query: &str) -> Search<'_> {
    let mut search = Vec::new();
    for pair in query.split('&') {
        if pair.is_empty() { continue; }

**Risk ledger.**
1. **oha may not show S moving.** E2 predicts +1…4 %, close to noise. The hard acceptance is criterion (robust, ≥ 5× on the contended numbers). oha S must only be ≥ before, and Step 1 of Task 6 STOPs rather than tunes.
2. **`ShardedLock` writer cost.** A write takes 8 sub-locks (86.7 ns measured). Writes are MISS inserts, invalidations and listener removals, all off the HIT path. A tag-invalidation of N keys does N writes under the gate. That is acceptable, and the same O(N) as today's moka loop.
3. **Listener inline in moka calls** (the deadlock class). Covered by the job-cache-proven discipline (front guard dropped before moka; the listener takes no stripe or gate) and by Review Focus 1's tests, ×20.
4. **`invalidate_path` semantics.** The count is now taken from the front (live entries) instead of `moka::iter()`. moka's iterator also skips expired entries, and front ⊇ moka's live set by the invariant. `invalidate_path_*` tests are unchanged.
